# 0.17.2 Testing Log

## Problem

In `RuidaRPAEncoder._handle_layer_start`, the GlueScript `declare_layer` call hardcoded `overscan="NONE"`. The ruidarpa adapter declares `native_overscan = True`, so the pipeline's OverscanTransformer disables its own toolpath-level overscan and relies on the controller's native overscan. Raster layers therefore emitted `OVERSCAN_OFF` and the controller never extended the scan past the image edges, producing edge under-burn. Separately, `_compute_layer_mode` only recognized VARIABLE_POWER and DEPTH_MAP raster sections; CONSTANT_POWER sections (produced by both full-swing and dithered engraving, which are indistinguishable in Ops — both are built by `Ops::from_mask_scan`) fell through to VECTOR mode, so raster layers were declared as vector layers.

## Solution

The encoder now derives the overscan from the layer's scan-line geometry. `_compute_overscan` scans forward from the LAYER_START, tracks the head position through MOVE_TO/LINE_TO commands, and on the first SCAN_LINE inside a RASTER_FILL section computes the scan angle: horizontal (≤1°) yields `X_BI`, vertical (≥89°) yields `Y_BI`, and diagonal yields `NONE` (the Ruida controller does not support diagonal overscan). VECTOR and DEPTHMAP layers keep `NONE` (GlueScript forces DEPTHMAP to NONE via its `_layer_modes` override; an upstream change request asks that this be removed). `_compute_layer_mode` now maps CONSTANT_POWER sections to the new `RASTER` layer mode, with priority DEPTHMAP > IMAGE > RASTER > VECTOR.

## Verification

Six new overscan tests lock in the behavior: horizontal → X_BI, vertical → Y_BI, diagonal → NONE, vector → NONE, RASTER-layer angle → X_BI, and no-scan-lines → NONE. The golden fixture was regenerated; the Engrave layer is now declared `declare_layer('Engrave', '#33cc33', 'IMAGE', 'X_BI', 2.5, 30.0, 50.0, 50.0)`. The full ruidarpa test suite passes (249 tests). flake8 and pyflakes pass with no new errors (ruff 70 and pyright 2 pre-existing, unchanged from baseline). A code review approved the overscan and layer-mode logic with no critical or major issues.

## Problem

The encoder clamped power settings via `_clamp_power_pct`, raising any power below 8% up to the controller minimum and logging a warning per clamp. Variable-power bit images frequently contain values outside the limits, so per-op clamping flooded the log. The user directed that the encoder stop clamping and pass raw power to GlueScript, letting it clamp as necessary. After the clamp was removed, a regression surfaced: binary (CONSTANT_POWER/DITHER) raster scan lines carry 0% power on off-pixels, and `_linearize_curve` fed those through `power_range(0.0, 0.0)`, which GlueScript rejects (min power < 8%), so full-swing and dithered raster jobs failed to encode.

## Solution

`_clamp_power_pct` and the `_MIN_LAYER_POWER_PERCENT` constant were removed; the encoder now passes raw power to GlueScript, which validates it (currently raising ValueError below its 8% minimum and warning above 70%). An upstream change request (`docs/prompts/ruida-pa-clamp-power.md`) asks ruida-pa to clamp instead of raise, and to honor DEPTHMAP overscan. `_linearize_curve` now tracks laser state: a zero-power pixel turns the laser off, so the head emits `move_xy_to` (rapid move) instead of cutting at 0% power; non-zero pixels behave as before.

## Verification

Three new tests cover the regression and the RASTER overscan path: `test_constant_power_scan_with_zero_pixels_emits_moves` (zero-pixel scan emits move_xy_to and never `power_range(0.0, 0.0)`), `test_raster_layer_overscan_uses_angle`, and `test_raster_layer_without_scan_lines_uses_none`. The two clamping tests were rewritten to assert `pytest.raises(ValueError)`, documenting the fail-fast behavior pending the upstream clamp. The golden fixture was regenerated: the Engrave layer's 0-pixels now emit `move_xy_to(1.0, 0.0)` and `move_xy_to(5.0, 0.0)` instead of `power(0.0)` + cut. The full ruidarpa test suite passes (249 tests, 0 failures). flake8 and pyflakes pass with no new errors. A code review approved the fix with no critical or major issues; the only residual is that non-zero sub-8% power values still raise in GlueScript's `power_range`, which is pre-existing and deferred to the upstream clamp request.

## Problem

For RASTER layers (CONSTANT_POWER raster sections, i.e. full-swing and dithered engraving), the gluescript layer actions were moves only — the horizontal scan lines should be cuts. `_linearize_curve` tracked a local `laser_on` flag and converted LINE_TO sub-ops to `move_xy_to` whenever the preceding SET_POWER sub-op carried 0.0 power. CONSTANT_POWER scan lines legitimately carry 0.0 power on off-pixels, and when the raster step's power was 0.0, every scan segment became a move, so the layer produced no cuts at all.

## Solution

`_linearize_curve` now branches on the active section's raster mode. For CONSTANT_POWER raster sections, every LINE_TO sub-op is emitted as `cut_xy_to` unconditionally and every SET_POWER sub-op is emitted through `_emit_power` including 0.0 (emitting `power_range(0.0, 0.0)` in the transcript as a verification marker) — cuts are never changed to moves. VARIABLE_POWER and DEPTH_MAP sections (greyscale/depthmap images) keep the laser-state logic where 0-power pixels become moves. A new upstream change request (`docs/prompts/raygeo-full-swing-raster-flag.md`) asks raygeo to add a full-swing flag to the Ops section params, since full-swing and dithered raster both surface as `RasterMode.CONSTANT_POWER` and are currently indistinguishable in Ops.

## Verification

`test_constant_power_scan_with_zero_pixels_emits_cuts` (rewritten, injecting a mock GlueScript) asserts `power_range(0.0, 0.0)` is called, `cut_xy_to` is called, and no scan segment becomes a move; `test_variable_power_scan_with_zero_pixels_emits_moves` confirms 0-pixels still become moves for VARIABLE_POWER sections. The full ruidarpa test suite passes (250 tests, 0 failures). flake8 and pyflakes pass with no new errors. A code review approved the fix with no critical or major issues. Note: CONSTANT_POWER raster with off-pixels now emits `power_range(0.0, 0.0)`, which current GlueScript rejects (min power < 8%) — a deliberate documented fail-fast pending the upstream clamp request in `docs/prompts/ruida-pa-clamp-power.md`.

## Problem

In `RuidaRPAAdapter._on_rpa_status`, CONNECTED and DISCONNECTED/TERMINATED status events were handled unconditionally: every event reset `_is_connected`, emitted `state_changed` and `connection_status_changed`, and DISCONNECTED/TERMINATED logged an "RPA disconnected" warning. Redundant events (for example repeated DISCONNECTED notifications while already disconnected) therefore produced spurious warnings and duplicate signal emissions. Separately, the connection poll loop tracked its own `prev_alive` edge detection and set `_is_connected` on its edges while emitting only `state_changed`; because `_on_rpa_status` gates on the shared `_is_connected`, a poll-loop-wins race could swallow the callback's `connection_status_changed` emission entirely, leaving `machine.connection_status` stale in the UI.

## Solution

`_on_rpa_status` is now edge-triggered: CONNECTED only acts when `not self._is_connected` (logging `logger.info("RPA connected")`), and DISCONNECTED/TERMINATED only act when `self._is_connected` (logging the "RPA disconnected" warning). The poll loop now emits `connection_status_changed` alongside `state_changed` on both of its `prev_alive` edges, making it authoritative so no genuine transition can go unnotified; duplicate emissions are deduplicated downstream in the controller (`machine.connection_status != status` guard). The shared transition logic (set `_is_connected`, set state, emit both signals, log) was consolidated into a `_set_connected` helper used by both the poll loop and the callback, with `connection_status_changed` emitted before `state_changed` so a raising `state_changed` receiver cannot lose the connection notification.

## Verification

`test_status_disconnected_transitions_state` and `test_status_terminated_transitions_state` were preconditioned with a real CONNECTED transition; `test_status_redundant_events_are_inert` asserts redundant events are inert no-ops with exactly one "RPA connected" and one "RPA disconnected" log each; `test_rpc_poll_emits_connection_status_on_edges` asserts the poll loop emits exactly one CONNECTED and one DISCONNECTED; `test_rpc_poll_wins_edge_then_late_callback_is_inert` reproduces the original race (poll wins the edge, late callback swallowed, exactly one emission per direction). The full ruidarpa test suite passes (252 tests, 2 pre-existing failures in test_encoder.py under ruida-pa 0.17.2 where GlueScript warns instead of raising for sub-8% power). flake8 and pyflakes pass with no new errors (ruff 70 and pyright 15 pre-existing, unchanged from baseline). Two code reviews approved the change with no critical or major issues.

## Problem

`RuidaRPAEncoder` treated each Rayforge layer as a Ruida layer: `_handle_layer_start` emitted the GlueScript `declare_layer` call, so a Rayforge layer with multiple workpieces produced a single Ruida layer spanning all of them. Ruida controllers (and ruida-pa) only support layers, so the correct mapping is one Ruida layer per Rayforge workpiece. Additionally, the encoder had no guard for a workpiece appearing outside a layer or a layer containing no workpiece, so malformed jobs could silently emit actions outside any declared Ruida layer.

## Solution

`declare_layer` moved from `_handle_layer_start` to `_handle_workpiece_start`: each Rayforge workpiece is now bounded by WORKPIECE_START/WORKPIECE_END and declared as its own Ruida layer, using the owning Rayforge layer's name and color for the label/color parameters. Mode and overscan are computed per-workpiece at WORKPIECE_START (the `_compute_layer_mode`/`_compute_overscan` scans now break on workpiece boundaries). `_handle_layer_start` is state-save only (records `_layer_uid`, increments `_layer_key`). Two fail-fast guards were added: an orphaned WORKPIECE_START (no preceding LAYER_START) raises, and a LAYER_END with no WORKPIECE_START raises. Dead state (`self._layer`, `_layer_index_by_uid`) was removed, and the `_emit_power` message plus four docstrings were updated to WORKPIECE_START semantics.

## Verification

All job-building tests in test_encoder.py gained workpiece boundaries; op-map tests were re-indexed (7 to 9 and 12 to 18 ops; declare_layer owners at ops 2/8/13); five new tests cover multi-workpiece declare_layer emission, per-workpiece mode derivation, LAYER_START emitting nothing, orphaned WORKPIECE_START, and empty-layer LAYER_END. The golden fixture was regenerated with workpiece boundaries (3 declare_layer lines, one per workpiece). The full ruidarpa test suite passes (257 tests, 2 pre-existing failures in test_encoder.py under ruida-pa 0.17.2 where GlueScript warns instead of raising for sub-8% power). flake8 and pyflakes pass with no new errors (ruff 70 and pyright 15 pre-existing, unchanged from baseline). A code review approved the change with no critical or major issues.
