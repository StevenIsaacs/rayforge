# 0.17.1 Testing Log

## Problem

ruida-pa was updated to version 0.17.1, in which `RpcRdDriver` now inherits `GlueScript`. Previously the ruidarpa `RuidaRPAEncoder` created and drove its own `GlueScript()` instance, and the adapter's TUI backend (`RpaRpcClient`) staged the encoder's complete transcript wholesale on the server via `_stage_gluescript_document`. With `RpcRdDriver` now a full GlueScript, this duplicated state and machinery, and the encoder no longer needed its own GlueScript instance — it should author directly into `RuidaRPAAdapter._backend`.

## Solution

`RuidaRPAEncoder` now accepts an optional injected `gluescript` argument. When one is provided, it authors ops into that GlueScript, resetting it for a fresh job via `new_gluescript()`; when none is provided it creates its own `GlueScript()` as before, so the preview path (intent_builder / cmd) is unchanged and byte-identical. The adapter's TUI backend was switched from `RpaRpcClient` to `RpcRdDriver`, unifying both connection modes behind a single GlueScript authoring path. The run path now re-encodes ops into the live backend and executes via `run_job()`, removing the wholesale `_stage_gluescript_document` and `_run_staged_job` machinery. Safety guards were added: `run_job()` is skipped when the re-encoded output is empty (so a stale prior job is never run), and on an encode failure the backend is torn down via `new_gluescript()` before re-raising the original error. Both connection modes neutralize the head and tail scripts, since `run_job()` composes head + job + tail and the default head is non-empty. The now-dead `RpaRpcClient` and its tests were removed.

## Verification

The full ruidarpa test suite passes: 234 tests across the encoder, adapter, direct driver, and golden tests. The golden fixture was regenerated for the new ruida-pa version; the diff is limited to the `# Generated by: GlueScript 0.16.2` to `# Generated by: GlueScript 0.17.1` header line, confirming no behavioral drift in the staged rpascript. A code review approved the refactor with no critical or major issues; the two minor findings (teardown masking the original encode error, and a clarifying comment on the connection-loss path) were addressed and re-verified.

## Problem

With ruida-pa and the ruidarpa driver connecting via RAC (TUI RPC mode), when the machine is off or disconnected and not responding to pings, the driver created a new `RpcRdDriver` instance on every reconnect attempt. Because the UDP transport's `open()` only binds a socket and never verifies that the peer responds, `start()` returned `True` even with the machine off, so each attempt registered a fresh set of status/error/reply listeners on the RPC server. The connection poll then found the server-side `is_connected` false and broke without closing the backend, relying on CPython refcounting and `__del__` for cleanup — but RPyC netrefs and the background serving thread create reference cycles that delay garbage collection, so the old driver's listeners stayed registered while the next attempt added another set. The result was unbounded listener accumulation on the server.

## Solution

The ruidarpa adapter now constructs a single `RpcRdDriver` lazily on the first connect attempt and reuses it across reconnect attempts. Listener registration is guarded by a `_listeners_registered` flag so the three listeners (status, error, reply) are registered at most once per instance. The backend is recreated only when a connect attempt raises an exception (e.g. transport death or `start()` returning false), at which point the old backend is explicitly stopped and closed before the next attempt constructs a fresh instance; this reset is scoped to TUI mode so direct mode keeps its persistent backend. The machine-off path (poll finds `is_connected` false) reuses the existing backend without recreating it. The direct driver (`RdDriver`) was already correct: it reuses a single `RpaDirectDriver` and unregisters listeners before re-registering them.

## Verification

The full ruidarpa test suite passes: 237 tests. Three new tests lock in the single-instance behavior: `test_rpc_reuses_single_instance_across_retries` (constructor called once across machine-off retries), `test_rpc_registers_listeners_once` (each listener registered exactly once), and `test_rpc_recreates_backend_on_exception` (backend recreated only on a transport exception, not on machine-off). The new tests were run five times consecutively with no flakiness. flake8, pyflakes, and pyright pass with no new errors. A code review approved the fix with no critical or major issues; the two minor findings (a single flag coupling three registrations, and no explicit machine-recovery test) are non-blocking.

## Problem

The connection loop reported "Connected" as soon as `start()` returned True. But the UDP transport's `open()` only binds a socket and never verifies that the peer responds, so the adapter announced a connection while the machine was off. The poll loop then treated every `is_connected == False` read as a connection loss: it logged "RPA connection lost", tore down the backend, and reconnected with backoff — so a machine-off episode produced repeated connect/lost warnings, repeated "reconnect attempt failed" warnings on every attempt, and connection-state flapping in the UI.

## Solution

The connection loop is now edge-triggered. `start()` succeeding only means the transport bound; the poll loop's `is_connected` read is the sole source of connection state. A False→True edge sets Connected (logging "Connected to Ruida controller via RPA" once) and a True→False edge sets Disconnected (logging "RPA connection lost" once); machine-off polling is otherwise quiet — no state flips, no warnings. The `_unreachable_warned` flag deduplicates the "RPA server unreachable" (TUI) / "RPA reconnect attempt failed" (direct) warnings to once per unreachable episode, reset when the server becomes reachable again ("RPA server reachable" logged once on recovery). The `_on_rpa_status` DISCONNECTED/TERMINATED branches were merged, and the redundant "RPA connected via RPC/direct" log in the CONNECTED branch was removed — the poll loop owns connection logging now. The dead `RpaRpcClient` source file (`rpa_rpc_client.py`) was also removed, completing the removal documented in the first entry of this log.

## Verification

The full ruidarpa test suite passes: 243 tests (was 237; the rework adds 6). The new `TestRpcEmitOnceLogging` class (5 tests) locks the emit-once behavior: machine-off polling is silent, "Connected" logs once on the False→True edge, "RPA connection lost" once on True→False, "RPA server unreachable" warns once, and "RPA server reachable" fires once on recovery. The existing single-instance tests were converted to assert quiet polling (`backend.start.call_count == 1`, `adapter._backend is backend`, `is_connected` reads via `PropertyMock`). flake8 and pyflakes pass on the changed files; ruff shows zero new errors (27 pre-existing in the changed files, identical rule set at HEAD).

All four findings were addressed: the dedup tests now force two consecutive exceptions and assert the warning count stays 1, the "logged once" assertions wait for additional polls before counting, the `ConnectionError` path logs "RPA connection attempt failed" instead of "RPA server unreachable", and the exception handler now sets `state.status` to UNKNOWN and fires `state_changed` (guarded so it does not re-fire on every reconnect attempt). ## Problem

In generated gluescript, job objects were rotated 180 degrees. Jogging was fine and job corners appeared correct (but may be because they too were rotated). The root cause was twofold. First, the adapter's `run()` re-encoded the world-space `JobArtifact.ops` directly into the live backend GlueScript, bypassing the pipeline's `job:machinexform` world→machine transform; the Ruida encoder passes coordinates through untransformed (it expects machine-space ops), so the controller interpreted world-space coordinates in its native top-right frame and rotated the job 180 degrees. Second, there was a philosophy mismatch: the encoder returned rpascript (the compiled output) as `encoded.text` and stashed the GlueScript transcript (the source) in `driver_data["rpa_gluescript"]`, which the pipeline strips — violating the ruida-pa philosophy that upper layers should only be concerned with the source, since rpascript is subject to change as more of the Ruida protocol is discovered.

## Solution

The encoder now returns the GlueScript transcript as `encoded.text` (the source) and no longer stages or compiles; rpascript is the compiled output produced by the backend. The adapter replays that machine-space transcript into the live backend via `stage_gluescript(transcript)` + `run_job()`, and no longer re-encodes world-space ops, so the 180° rotation is fixed. Op-map bookkeeping was rewritten to transcript spans (with an `end > start` guard and clamping to the final transcript length), `_job_started`/`_job_ended` framing flags were added with a `RuntimeError` for incomplete jobs, and the golden fixture was regenerated as the transcript with a staging smoke test that verifies the compiled rpascript.

## Verification

The full ruidarpa test suite passes: 242 tests across the encoder, adapter, direct driver, and golden tests. flake8, pyflakes, and pyright pass with no new errors (ruff 70 vs the 76 baseline). A code review approved the refactor with no critical or major issues; the minor findings were documented as todos in ToDo.md. Manual testing on hardware confirmed the fix: job objects in generated gluescript are no longer rotated 180 degrees.
